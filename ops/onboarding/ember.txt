===============================================================================
0. WHY THIS FILE EXISTS, AND WHAT IT ASSUMES
===============================================================================

Bolt and GreenBear have had a cold-start runbook for some time. Ember has worked
without one, which means every session started by reconstructing the procedure
from memory - the exact failure mode the cold-start protocol exists to prevent.
This is the first version, written to match the other two.

It is written against AGENTS.md **v2.0.0** on origin/main, which carries two
Owner decisions from 2026-07-29:

  THERE ARE NO ROLES. NO DIRECTOR, NO HEAD OF THE TECHNICAL GROUP, NO GATE
  HOLDER. ALL AGENTS ARE EQUAL.
  ANY AGENT WHO KNOWS HOW MAY DEPLOY - ONE AT A TIME, AND ONLY AFTER PROVING
  EVERY GATE CHECK PASSED.

  NO POLLERS. DO NOT START ONE, FOR ANY CHANNEL, AT ANY INTERVAL.
  A CARPET MESSAGE SIGNALS BY ITSELF WHEN IT ARRIVES.
  THE CHAT AT :8799 IS SWITCHED OFF - BUT KEEP IT. THE OWNER WILL WANT IT BACK.

One consequence is specifically Ember's, because of how Ember has actually
worked: **the deploy gate is no longer a seat anyone holds.** Ember has been the
one checking other agents' work and clearing or refusing it. That authority is
gone - not because the checking was wrong, but because it made shipping wait on
one agent being available. What survives, and is now written into section 8 of
the constitution, is the part that was always the valuable half: a second pair of
eyes that disagrees with evidence. Anyone may still say "this is broken, here is
the measurement". Nobody may say "you may not ship".

An unknown to settle in the first session, not assumed here: **which machine
Ember runs on.** Bolt is on DESKTOP-ODD5QN8; GreenBear is on a different
computer. Discover and record this machine's hostname and repository path
(section 2). Never use another agent's checkout or processes.

Hard rules:

1. This is a clean-slate cold start. Messages and orders older than this cold
   start are audit history, not active commands.
2. Do not inherit an old STOP, FREEZE, ROLLBACK, task, or work package from
   logs, journals, or state files.
3. Do not modify project code during onboarding.
4. Do not use pull, checkout, merge, reset, clean, stash, commit, push, deploy,
   migration, or test commands during onboarding. git fetch origin is required.
5. Do not trust the local branch or local copies of governance documents.
6. Read the five documents from origin/main, in the required order.
7. DO NOT START A POLLER. Not for Carpet, not for Telegram, not for anything,

9. Never pass non-ASCII text as a curl, shell, or command-line argument. The

   header does not save it.
10. Every JSON request body containing text must be produced by json.dumps and
    encoded as ASCII.
11. No agent commands another agent, and no agent waits for another agent's

13. Sign every direct message to the Owner with "Ember:".
14. Never write to the Owner on Carpet. He does not read it.
15. Never stop, rewrite, or repurpose another agent's files or processes.
16. Onboarding does not authorize a deploy. Deploying is section 7, and it
    requires an open turn and a complete gate record.

Record the cold-start boundary before reading any history:

PowerShell:

  [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
  $OutputEncoding = [Console]::OutputEncoding
  $OnboardingStartedUtc = [DateTime]::UtcNow.ToString("o")

POSIX:

  OnboardingStartedUtc=$(date -u +"%Y-%m-%dT%H:%M:%S.%NZ")
  printf '%s\n' "$OnboardingStartedUtc"

Only messages newer than that timestamp can be current.

===============================================================================

Locate the inner CulinEire Git repository on THIS machine - the directory that
contains .git and AGENTS.md.

  hostname

  git -C $RepoRoot rev-parse --show-toplevel

If fetch fails, report the exact error. Do not continue on stale remote refs.

**Check the git identity before the first commit of every session:**

  git -C $RepoRoot config user.name
  git -C $RepoRoot config user.email

Recorded 2026-07-29: several commits on origin/main are authored by `YourName` -
an unconfigured git default. Those commits are on the shared history and nobody
can now tell which agent or machine made them. Authorship is the cheapest audit

If `user.name` reads `YourName`, or anything that is not a real identity, report
it to the Owner and ask what it should be set to. Do not silently pick one - the

===============================================================================
4. VERIFY GIT WITHOUT MODIFYING IT
===============================================================================

  git -C $RepoRoot status --short
  git -C $RepoRoot branch --show-current
  git -C $RepoRoot rev-parse HEAD
  git -C $RepoRoot rev-parse origin/main
  git -C $RepoRoot log --oneline -5
  git -C $RepoRoot remote -v
  hostname

Interpretation:

- A local HEAD different from origin/main is evidence, not permission to switch
  branches.
- A branch named agent/ember/* is Ember-owned. Record it.
- A branch owned by another agent must not be reused.
- Any status output means working_tree_clean: false.
- If the tree is dirty, do not stash, discard, reset, clean, commit, or absorb
  the changes.
- Record BLOCKED_FOR_IMPLEMENTATION only when the checkout belongs to another
  agent, or a fresh Owner STOP is active. Otherwise READY_AWAITING_ORDER, even
  with a dirty tree.
- Do not invent a branch without a card.

Also reconcile against production before claiming anything is missing:

  git -C $RepoRoot log --oneline -12 origin/main
  # then read the footer version live on https://culineire.ie/

Work remembered from a previous session may already have shipped. Prove absence;
never assume it.

5. CARPET - THE AGENT CHANNEL, WITH NO POLLER
===============================================================================

Carpet is the coworking app in this repository. It carries agent-to-agent
coordination and the audit trail of decisions. It is NOT for the Owner.

  AN ARRIVING MESSAGE SIGNALS BY ITSELF. THERE IS NOTHING TO POLL.

Do not start a poller, a supervisor, a heartbeat writer, a watcher loop, or a
scheduled wake-up. Do not check "just in case" between tasks: confirming that
nothing arrived costs the Owner money and returns no information.

During onboarding, do not read Carpet history at all. Messages older than
OnboardingStartedUtc are audit history, not active commands, and reading them
invites acting on a dead order.

To SEND to another agent, write a Python file, copy it to the server, run it
under the server venv, and delete it. Inline heredocs break on quoting.

  agent ids are lowercase and case sensitive: "ember", "bolt", "greenbear".
  A capitalised id silently creates a SECOND mailbox and the message is lost
  while the sender sees SENT.

  Every message body is serialised with json.dumps and sent as pure ASCII.

If a STOP, FREEZE or ROLLBACK arrives after OnboardingStartedUtc it is active
immediately: start nothing new, stop cancellable commands safely, avoid commit,
push, merge, migration and deploy, preserve the working state without
destructive commands, and report STOPPED.

===============================================================================
6. WORKING BY THE BOARD
===============================================================================

The board dispatches the work. No agent hands out tasks, and no agent picks up a
card that is not theirs.

1. Read docs/ARENA_BATTLE_PLAN.md on origin/main. Find the NEXT card and its
   suggested owner. A suggested owner is a hint about who is best placed, not a
   role and not an assignment.
2. Cards run STRICTLY one at a time, in table order. Card N+1 does not start
   until card N is DONE - merged, deployed and verified.
3. Each agent holds at most one card.
4. The Owner assigns the card. Do not self-assign, and do not start a card whose
   prerequisites are not DONE.
5. Work in one disposable worktree off current origin/main. Check file overlap
   before editing; one file has one owner during an active card.
6. Focused PostgreSQL tests only - never SQLite, where select_for_update is a
   silent no-op and every row lock runs untested while the suite reports green.
   The full suite belongs to the final gate, not to every slice.
7. Return, as the card's evidence: exact commit and changed files, the stated
   visible result, every acceptance statement checked, confirmation that each
   forbidden change was avoided, and test, check and diff output.
8. Close the temporary branch and worktree after the slice is deployed.
9. Write the progress into the journals in the same session. Work that is not in
   the journals did not happen, whatever the commit log says.

Scope discipline, which survives every reorganisation:

- Do exactly the assigned card. Record unrelated findings; do not fix them.
- Do not classify code as dead without evidence from every surface: imports,
  URL reverses, templates, CSS, JS, settings, admin, management commands, tests,
  migrations.
- Never delete an asset the Owner paid for or approved, and never delete a
  working UI element. Disconnect instead - one line, and reversible.
- Mass deletion only by EXACT pattern: count first, show ten examples, list the
  survivors, then delete.
- Never soften a failing check to make a suite green.

### Checking another agent's work

This used to be Ember's standing job and is now everyone's, so the rules that
made it useful are worth keeping explicit:

- A check that agrees with everything is not a check.
- Disagree with **evidence** - the diff, the measurement, the failing test - and
  address it to the agent and to the Owner. That is a finding, not a veto.
- An agent whose work is challenged answers the evidence, not the challenger.
- Nobody's conclusions are exempt, including the conclusions of whoever wrote
  this file.
- Do not block. Since 2026-07-29 there is no authority to withhold a deploy;
  there is only the authority of a demonstrated fault, which is stronger.

7. DEPLOYING - ANY AGENT MAY, ONE AT A TIME, GATE FIRST
===============================================================================

Owner's decision, 2026-07-29: nobody guards the gate and nobody grants
permission. Every agent who knows how may deploy their own work. Two conditions,
and neither is negotiable.

CONDITION 1 - THE TURN. Only one deploy is ever in flight, across all machines.

If .agent-chat/deploy.lock on the chat host is reachable, claim it there: write
the agent name, the UTC start, the version and the commit; remove it the moment
the deploy is verified or abandoned. If a lock is present, wait. Do not deploy
in parallel and do not assume a lock is stale. A lock older than 60 minutes is
reported to the Owner, naming the agent in it, and cleared only with his word.

If the shared path is NOT reachable from this machine, the turn is claimed by
telling the Owner, before shipping, that Ember is taking the deploy turn - and
waiting for him to confirm nobody else holds it. He agreed to act as that
signal on 2026-07-29.

CONDITION 2 - THE GATE. Re-read AGENTS.md sections 8 and 17 FROM THE FILE, not
from memory, every single time. Then run every check and record the result. With
no second pair of eyes standing at the gate any more, this written record is what
replaces review - it is not a formality and not optional.

  pre_deploy_reread:
    constitution_version: ""      # read from the file, not recalled
    sections_reread: ["8", "17"]
    rules_that_apply_here: []     # named, not "all of them"
    index_read: false             # git status --short + git diff --cached --stat
    files_in_commit: 0            # must match what the card names
    base_verified: ""             # the origin/main hash this work stands on
    already_exists_checked: false # proven absent from main and from production
    gates: []                     # image weight test, focused tests, diff --check
    version_bumped: false         # footer version in templates/base.html
    collectstatic_run: false      # required when CSS, JS or images changed
    rollback_command: ""          # stated, and it resolves
    screen_change_in_one_line: "" # what the Owner will SEE, or plainly nothing

Shipping past a red gate is forbidden. A failing test is the mechanism working,
not an obstacle to route around.

Still excluded and still needing the Owner's explicit word every time: payment,
payout, Stripe, legal, privacy, moderation policy, database migrations, and any
change to a schema or a public access gate.

Still true regardless of who deploys:

- the author of a change is accountable for its gate record;
- a deploy is not a release - Arena visibility stays staff and superuser only
  until the Owner separately opens it;
- never run Django on the server as root, use sudo -u deploy - root-owned files
  break production silently;
- "RESTARTED" is not "deployed" - collectstatic can fail silently and the site
  keeps serving the old hashed file. Verify the live file over HTTP, not the
  fact of a restart.

After the deploy, in the same working session:

- write the version and what shipped into config/release_journal.py;
- move the card's status and evidence in docs/ARENA_BATTLE_PLAN.md;
- update the board rows in recipes/views.py ARENA_RELEASE_STAGES;
- release the turn lock, or tell the Owner the turn is free;
- tell the Owner in one line what changed on his screen.

A board that is not deployed has not moved.

8. TALKING TO THE OWNER
===============================================================================

The Owner is the only one who assigns cards and the only one who accepts a
result. Talk to him directly, in this session window or the ops Telegram bot -
never on Carpet, which he does not read.

Rules:

- Sign every message "Ember:".
- Answer in Russian.
- Numbers and a decision, not a status narration.
- Do not repeat a blocker that has not changed.
- Do not ask a question whose answer does not change the output.
- Do not re-ask something he has already answered.
- Cut the volume, and put the answer in the FIRST line. Recorded 2026-07-29: an
  agent buried a recommendation in the fourth paragraph, the Owner did not see
  it, and asked the same question again. An answer he does not reach does not
  exist.
- Never take a PRODUCT decision yourself - what appears on the screen, what
  colour it is, what geometry it has. A technical choice inside an assigned card
  is yours; the product is his. If two sources disagree, do not pick the more
  authoritative one - name both and ask.

ANYTHING THAT NEEDS HIS CONFIRMATION IS MARKED RED.

In this terminal, red text is produced with a diff code fence whose lines start
with a minus:

  ```diff
  - Need your word: <the question, in one line>
  ```

Under every red block, offer the answers - and this is the part that was got
wrong on the first attempt, so it is spelled out:

  EVERY ANSWER GETS ITS OWN FENCED CODE BLOCK.

The terminal draws a copy button per code block, not per line. Four answers
listed inside one block give him ONE button that copies all four at once - which
is exactly what happened on 2026-07-29: he pasted all three options back,
because that is what the single button gave him.

The Owner has one keyboard shared across three computers and switching it is
physically awkward. A copy button he can click with the mouse is not a nicety;
it is the difference between answering and not answering.

  WRONG - one block, one button, four answers glued together:

    ```
    деплой
    не деплой
    покажи скриншот
    отложи
    ```

  RIGHT - one block per answer, one button per answer:

    ```
    деплой
    ```

    ```
    не деплой
    ```

Say "выбери один" above them when the options are mutually exclusive. Keep each
answer to one short line. He is clicking, not composing.
